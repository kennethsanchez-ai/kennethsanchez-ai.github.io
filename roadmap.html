Current project status

v2.2.0 is the current completed release. Its private GitHub release and validated artifacts are published, the release commit was integrated into main by fast-forward, and post-release documentation was finalized. Release and main CI succeeded. The public project website provides an overview and technical documentation; it does not distribute the application or expose private release assets.

The sequence below is based on tagged source history and release records. “Completed” means the code and recorded validation for that version exist. It does not imply provider access approval, live validation, deployment, or public download availability.

v2.0.0 — trust and evidence foundations

Completed. This release established explicit provider trust metadata, runtime health monitoring, registration/onboarding descriptions, and stronger manual-offer validation. Provider capabilities and trust became separate concepts so that an implemented operation would not itself grant production eligibility.

  • Explicit source authorization, evaluation-only status, production eligibility, verification, and consumer-total assurance.
  • Runtime health observations separate from static trust policy.
  • Validated manual offers and a fixture-only KAYAK evaluation mapping, without claiming a live integration.
  • Price Intelligence 2.0 foundations for compatible historical evidence, freshness, volatility, and deterministic confidence.
  • A read-only Price Intelligence text CLI that did not change recommendation ranking.

These foundations explain why later reporting can describe trust, health, and price evidence without merging those responsibilities. An adapter’s presence in source does not establish source approval or production readiness.

v2.1.0 — structured, safer reports

Completed. v2.1.0 added structured Price Intelligence JSON output to stdout and read-only Provider Status text/JSON reporting. Those existing capabilities are distinct from v2.2.0’s later file export and additional diagnostics.

  • Schema-versioned Price Intelligence JSON with safe, explicit fields.
  • Provider Status reporting of static metadata and persisted operational health.
  • Hardened malformed persisted-data handling and allowlisted warnings instead of raw payload/error disclosure.
  • README package metadata and a test-only dependency adjustment supporting warning-free TestClient validation.

Reporting continued to leave recommendation ranking, search coordination, API behavior, and database migrations unchanged. Safer parsing was a reporting boundary, not a way to turn malformed observations into trusted offers.

v2.2.0 — reporting mechanics consolidation

Completed. Three milestones expanded observability while retaining the existing reporting contract.

  1. JSON file export: exclusive creation, no overwrite or automatic parent directory, UTF-8 LF output, serialization before file creation, and silent stdout on success.
  2. Provider diagnostics: authoritative current UTC-month usage counts, a bounded recent-event count, strictly parsed HTTP status fields, and descriptive health ages.
  3. Shared serialization: common whole-second UTC timestamps and deterministic strict JSON with one trailing newline.

The release retains schema version "1"; Provider Status includes the planned quota and health-age additions. It passed 428 local tests and successful Python 3.12, Python 3.13, and container/build CI. File-export equivalence, offline smoke tests, package metadata, archive contents, and downloaded artifact hashes were verified.

Search behavior, ranking/tie-break rules, trust and eligibility, quota enforcement, dependencies, API contracts, and database schema were not changed by these milestones. The known missing sdist fixture observation remains nonblocking. See validation scope for the limits behind these results.

Future work — approval-dependent, not scheduled

The documented forward direction is integration with an explicitly approved hotel-rate source. Source-onboarding documentation requires written permission for the intended automated use, documented schemas and terms, rate/caching/storage limits, sandbox checks, and separate production enablement approval.

  1. Confirm a documented, permitted rate-access route and its allowed use.
  2. Obtain the necessary access and usage terms through the provider’s official process.
  3. Develop or adapt against documented schemas with fixtures and sandbox validation.
  4. Validate quota behavior, offer completeness, and re-verification before separately approved activation.

This is a gated direction, not a promise that an application has been accepted, that a source is enabled, or that live validation is complete. Existing evaluation or synthetic mappings do not satisfy those gates by themselves.

No v2.3.0 scope, completion date, production launch, or public package release is committed here. Future versions and schedules remain unspecified. This documentation adds no new product commitments beyond the existing approval-dependent source-onboarding direction.
