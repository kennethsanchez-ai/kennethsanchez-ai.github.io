A private decision-support system

Hotel Deal Hunter AI combines configurable hotel searches, normalized offers, recommendation scoring, and historical-price reporting. It supports personal travel decisions; it is not a booking service, a universal live-rate feed, or a publicly deployed application. This overview describes the v2.2.0 implementation and its tested boundaries.

The CLI is the operator entry point. Configuration and an optional named profile define destination, dates, occupancy, budget, and flexibility. A search coordinator uses a strategy component to choose the next configured provider or a verification decision. Adapter implementations translate source-specific responses into a common offer model. Recommendation and reporting components then work with normalized data rather than vendor response formats.

Two paths through the system

The scan strategy considers the current best price, target and maximum budgets, remaining providers, and permitted expansion decisions. The coordinator controls which decisions are executed. A strategy capability is not evidence that an external source has been approved or exercised live.

Provider abstraction and trust

Providers share search and verification interfaces and declare capabilities separately from trust. Capabilities describe supported operations; trust describes source authorization, evaluation-only status, production eligibility, verification level, and consumer-total assurance. Configuration may narrow declared trust but cannot upgrade it.

Normalization, price completeness, and eligibility checks prevent an incomplete or evaluation-only result from becoming a trusted production recommendation merely because a request succeeded. Manual inputs also require validation. Fixture-based adapter mapping demonstrates parsing behavior; it does not establish an approved, runnable live integration.

Runtime health records success, failure, latency, and recent activity. It is observational. A healthy response does not grant authorization, and an unhealthy record does not rewrite the static trust policy or ranking rules.

Price Intelligence and diagnostics

Price Intelligence evaluates saved offers against the target budget and compatible historical observations. Compatibility includes hotel, stay dates, currency, room type, occupancy, and trusted all-in-price evidence. Historical median, recent low, and volatility evidence require at least three compatible observations; limited evidence is reported as such. Price freshness and confidence explain evidence quality rather than guaranteeing a future rate.

The read-only Price Intelligence CLI is separate from recommendation ranking. Its report does not change search order, ranking scores, or tie-break rules. Provider Status similarly combines static registration metadata with allowlisted persisted health and usage fields; it does not instantiate providers or launch a fresh health probe.

Persistence and side-effect boundaries

Repository interfaces encapsulate observations, health, usage activity, and operational records. SQLite is used by the report CLI. A separate repository factory supports PostgreSQL for configured consumers, with migration SQL included in distributions. That support does not mean these CLI reports read arbitrary PostgreSQL deployments.

Report commands open an existing local history database without initializing a missing one. They do not write health or quota records. The explicit Price Intelligence file export is the reporting path’s requested write: a new file in an existing directory. Search and monitoring are different paths and can perform provider calls and persistence.

Design decisions that preserve boundaries

Deterministic reporting
Shared UTC formatting and strict JSON serialization keep output predictable while leaving document construction and redaction with each report.
Enforcement versus observation
Provider quota controls govern calls. Provider Status reports historical activity, not allowance, exhaustion, or enforcement decisions.
Fail-closed evidence
Malformed persisted rows produce bounded, allowlisted warnings instead of raw payloads or trusted fallback offers.
Stable behavior
v2.2.0 adds reporting mechanics without changing recommendation ranking, provider eligibility, API contracts, or database schema.
